Persistence

A stale save can never overwrite newer state

The risk: two saves race, and the older snapshot lands last.

Merge-on-write: lock the row, merge stored and incoming state, write back.

Why it’s safe: CRDT merges are order-independent, so the result always contains every update either save carried.

BEGIN;
SELECT ydoc FROM "Document"
WHERE id = $1 FOR UPDATE;
-- merged = Y.mergeUpdates([stored, incoming])
UPDATE "Document" SET ydoc = merged
WHERE id = $1;
COMMIT;

Saves are batched (1 s after typing stops, at least every 5 s) and flushed on shutdown. Documents load before anyone can join.

Persistence is where a naive design quietly loses data. Hocuspocus saves the document in the background, debounced. If two saves overlap — say a slow save finishes after a newer one — a plain overwrite would replace newer content with older. My approach is merge-on-write: inside a transaction, lock the document’s row, read what’s stored, merge it with the incoming state using Yjs’s own merge function, and write the result. Because CRDT merges are commutative and idempotent, it does not matter which save lands first: the stored state always ends up as the union of both. The row lock just makes the read-merge-write atomic. Saves happen one second after typing pauses and at least every five seconds; on a normal shutdown the server flushes everything before exiting — that’s tested by actually killing and restarting the server in the test suite.
