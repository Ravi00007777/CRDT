A bug the tests caught

Revoking access from a live session

First attempt

Close the room

The library’s close only ends one document channel. The client marks itself signed-out and never retries, so even users who still had access got stuck.

Fix

Close the sockets

Every client reconnects and re-authenticates. Allowed users rejoin without noticing; the removed user is refused and sent to the dashboard.

Found by the integration test “share, then revoke”, which timed out until the fix.

One finding worth telling, because it shows why the tests mattered. When an owner removes a collaborator or deletes a document, anyone currently connected must lose access immediately. My first version used the library’s built-in “close connections for this document”. The integration test for share-then-revoke hung. Reading the library source, the reason was that this call only closes the per-document channel inside a shared WebSocket; the client marks itself unauthenticated and never re-sends credentials — so the removed user is cut off, but so is everyone else, silently. The fix is to close the underlying sockets for that room. Every client’s provider then reconnects and authenticates from scratch: users who still have access rejoin transparently, and the removed user is rejected and redirected to the dashboard with a notice. The same test now passes consistently.
